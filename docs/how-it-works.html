Rapid Autonomous Pipeline for Iterative Development

RAPID · RAPID
How it works

A gate-enforced pipeline that turns a vague idea or a stakeholder PRD into a tested, audited, deployed system — by separating the agent that builds from the agents that audit, structurally.
REPO  rapid-workflow METHOD  RAPID SKILL  /rapid-workflow VERSION  v0.5.0 AUTHOR  Johnny Chung
The core principle
One agent can't both build and audit honestly — so RAPID splits the roles structurally
The one-line thesis
The agent that writes the code must never be the agent that audits it. When one agent does both, visible progress (a working app) always beats invisible safety (tests, reviews, assertions). RAPID separates those roles with hooks, separate terminals, and tiered reviewers — not with prose that fails under pressure.
Why prose fails — an incentive misalignment, not a discipline problem
  • The protocol says "do X before proceeding."
  • X produces no visible output — tests, reviews, coverage.
  • The next step does produce visible output — working code, a deploy.
  • Under time or context pressure, the coder skips X and does the exciting thing. Every time.
The fix is structural, not behavioral
  • Hooks (R1, R7–R9) — make advancing, stopping early, or shipping a stub mechanically impossible.
  • A separate watchdog (R2) — its only job is auditing; no implementation incentive.
  • Blocking dependencies (R4) — the eval harness is task-00, not a prose reminder.
  • Tiered reviewers — separate subagents the coder's context can't pressure.
Reading ruleIf you see a step described in words but not enforced by a hook, a dependency, or a separate agent — that step will eventually be skipped. Every enforcement mechanism in RAPID exists because a real build skipped a prose instruction.

RAPID · How it works03 — The machine
Deterministic vs. dynamic
The pipeline is fixed; everything inside it is composed fresh for each project
RAPID is not a fixed system — it is a dynamic workflow template that generates a project-specific build system every time it runs. The scaffold never changes; the orchestrator selects and configures a framework for each phase from a library. No two RAPID builds produce the same architecture.

Immutable eval harness (R4)
After P5 the harness is read-only. A test that fails because the system is wrong stays failing — agents never edit a test to make it pass (Constitution Art. VII). This is what makes "compiles ≠ works" mechanical.
Why a diff, not a copyTwo parallel docs drift within a week. The diff is the value: every PRD requirement maps to a spec section or an explicit out-of-scope tag, and it becomes the change log when the gap loop fires.
RAPID · How it works08 — Arc 2: Specify
Spotlight · users → scenarios → tests
A Users panel names every hands-on persona — and their scenarios become the test suite
Before there is a test suite, there is a question: who actually touches this app? A Users panel enumerates every hands-on persona — not just the primary end user, but operators, admins, reviewers, support, and the people standing at the gates — and authors a detailed workflow and scenarios for each. Those scenarios are not thrown away: they are the source the immutable eval harness and the Workflow Test Theater are generated from.
Users panelevery hands-on persona→ User workflow mapdata-in · processing · data-out per node→ Eval harnessimmutable after P5→ Workflow Test Theaterrunnable · recorded
What the Users panel produces
  • A persona roster — every human who touches the app, each with their goal and their stakes.
  • A golden-path scenario per persona, written as concrete steps.
  • Named edge-case & failure scenarios — the branches agents and humans actually hit.
  • The gate operators count as users too — their review flow is a workflow with tests.
Why a scenario is already a test
  • Each node declares data-in / processing / data-out → maps straight to arrange / act / assert.
  • Branches and failure paths become the negative tests.
  • Coverage is reportable by persona and node — a missing persona is a missing test, and a bug you won't catch.
  • Each workflow is a runnable, recorded test in the Theater (docs/workflows.json).
Where it livesP2 (the user-panel lens) names the personas · P5 maps each one's workflow → users.html · P5/P7 generate the immutable eval harness + Workflow Test Theater from those maps. State that isn't drawn is state that breaks in production.

Gates are pre-screened, not raw
Before a gate reaches the operator, four document-review agents — feasibility, scope guardian, coherence, and adversarial — read the artifact through the project's pillars and flag issues. The human spends attention on judgment calls, not proofreading. Between gates, the build runs to completion under standing authorization (Arc 2/3), stopping only for the fixed stop-condition set: destructive, outward-facing, spends-money, or a genuinely-undecidable high-stakes call.
RAPID · How it works11 — Four human gates
Deep dive · the build phase (P6)
P6 runs a five-lead build team where the writer is never the auditor

The invariant — coder ≠ tester / reviewer / watchdog
  • One long-lived terminal per lead, connected via claude-peers (12 message types, JSON envelope).
  • The coder runs 1–4 coder terminals only for long, interdependent tasks; otherwise fans out coding subagents — bounded parallelism.
  • The watchdog is never a coder — its only output is audit findings, so it has no incentive to skip them.
  • Beyond a fan-out of 4, the reviewer can't honestly check every diff and review stops being meaningful.

RAPID · How it works12 — P6: the five-lead team
Deep dive · review & test
Code is reviewed by five confidence-gated lenses and tested across three viewports before it merges
Tiered review — different lenses find different bugs
  • Per-dimension review subagents (correctness · security · perf · …), each a separate subagent the coder's context can't pressure.
  • Confidence gating suppresses low-confidence noise; findings are de-duplicated across reviewers.
  • Weights shift by domain — security heaviest for healthcare, performance for real-time, correctness for financial.
  • Backed by the review, simplify, security-review, and eval skills.
Why separate, not one reviewer
One reviewer reading 8 parallel diffs misses things a focused lens catches. Per-dimension reviewers + dedup beats one broad pass.
Test + visual QA against the locked harness
  • Immutable evals (task-00) run first — the harness is the spec.
  • Playwright flows derived from the workflow map exercise the golden path + named edge cases.
  • 3 viewports, with screenshot evidence compared to the hi-fi comps approved at G2.
  • Integration tests hit real sandboxed DBs/APIs — not mocks (Constitution Art. VII).
Agent-first walkthrough
Agents walk the app mechanically before any human looks. The human becomes the felt-sense filter — "does this feel right?" — not the regression hunter.
RAPID · How it works13 — Review & test
Deep dive · safety by construction
Five mechanisms make P6 safe by construction, not by good intentions
R2 Separate auditor
The watchdog ≠ any coder — the builder structurally cannot skip its own safety checks.
R4 Immutable evals
.rapid/EVAL/ is locked after P5. Tests are the spec; code follows. No "fixing" a test to pass.
Keep-or-revert
Any regression after a merge → git reset --hard. Only improvements survive the ratchet.
C Worktree isolation
Each writer records its worktree/branch on SPAWN; worktree-check.sh fails the P6 exit gate if any writer skipped isolation or two shared one.
Cost breaker
Pauses at 80% of the token budget, forcing an explicit human choice instead of a silent overrun.
Shutdown handshake
P6e tears the team down cleanly and writes P6_EXIT.json — the gate the next phase reads.
The patternEach mechanism replaces a hoped-for behavior with a verified fact. The skill instructs isolation; worktree-check.sh verifies it — and a build that fanned writers into the shared tree mechanically fails the gate.
RAPID · How it works14 — P6 safety mechanisms
The enforcement layer · hooks
Every safety step is a hook, a dependency, or a separate agent — never just a sentence
This is where the thesis becomes mechanical. Prose can be ignored under pressure; hooks cannot. Hooks fire on Claude Code's PreToolUse / PostToolUse / stop events — the harness runs them, not the agent.
IDHookWhat it enforces
R1phase-gate-hook.shCan't advance without artifacts. Blocks a write to STATE.json unless the target phase's required artifacts exist — e.g. no P6 without ≥1 eval file, TASKS.json, and a fully-resolved INPUTS.json; no P7 without a passing P6_EXIT.json.
R7stop-hook.shCan't stop early. The inverse of R1 — a continuation hook that makes it mechanically impossible to halt before the build is actually done.
R8module-conformance-hook.shCan't drift silently. Traces every completed module back to spec → PRD → architecture and files a gap on any break.
R9stub-detect-hook.shCan't ship a placeholder. Detects stub/placeholder code as it's written; the ship gate (R9 + ship-gate.sh) blocks release on unresolved stubs in required modules.
—post-write-hook.shKeeps docs live. On a STATE write, refreshes the docs registry; on writes to numbered folders / decisions / panels / tests, appends a timestamped row to CHANGES.md. No post-build cleanup.
Installtools/install-hooks.sh wires these into the project's .claude/settings.json; preflight.sh checks the environment before a run.
RAPID · How it works15 — Hooks over prose
The enforcement layer · fail-closed
The gates fail closed: a build can't enter P6 or ship until its inputs and stubs are resolved
B · the inputs ledger — gather human input up front, made mechanical
  • inputs-check.sh reads .rapid/INPUTS.json and blocks P6 entry until every required input is resolved or waived.
  • Required inputs: credentials, deploy target, spend ceiling, resolved undecidables.
  • A credential row only counts resolved once its .env:KEY actually exists — not when someone says it's handled.
  • Run at G2; the phase-gate hook runs the same check independently.
Why fail-closed
This turns "gather all human input up front, then run to completion" from a hope into a precondition — the build literally cannot start the autonomous arc with a hole in its inputs.
Verified, not instructed
C · worktree-check.shAt P6 exit, asserts every parallel writer ran in its own declared worktree — merges build_writers_isolated into P6_EXIT.json.
R9 · ship-gate.shAt G3, blocks release while required modules still contain stubs.
E · mock-init.shAt P4, scaffolds the hi-fi design system + screen inventory so the backend is built to serve real screens; comps become P7's visual target.
The shapeEach verifier checks what the skill only instructed. Instruction + verification is the whole game — the verifier is what the gate actually trusts.
RAPID · How it works16 — Fail-closed gates
Governance · the Constitution
Ten articles govern every agent action; the first five can never be overridden
Articles I–V · inviolable · no override
ITruthfulness — no invented facts, citations, or test results. "Tests pass" requires verified execution.
IIUser safety — no unmoderated content to an end user; sandbox boundaries are inviolable.
IIIData handling — no PII off-device without consent; secrets never committed; COPPA/FERPA binding.
IVReversibility — destructive ops (rm -rf, reset --hard, force-push) require explicit confirmation.
VScope discipline — agents stay inside their declared R/W contract; out-of-scope access is a violation.
Articles VI–X · overridable only with # OVERRIDE + logging
VISpec authority — when behavior conflicts with the spec, the spec wins; raise a gap.
VIINo test theater — real sandboxed DBs/APIs; a wrong-system test stays failing.
VIIIHonest reporting — report what was actually done, verified in the actual file.
IXPushback discipline — don't capitulate without a reason; don't invent one either.
XRoot-cause discipline — no papering over symptoms with try/except, retries, fallbacks.
EnforcementThe watchdog audits every diff against I–V before merge · the gap classifier tags violations in 08-gaps/HISTORY.md · the retrospective reviews every VI–X override each cycle. A copy of the Constitution sits at the generated project's root.

Cost & touchpoints

cost-summary.sh parses real billed tokens from Claude Code transcripts per step / session / project — then attributes them per RAPID phase by bucketing each step into the phase active in the observe timeline, and counts human touchpoints per phase (GATE + ESCALATE events + needs-real-human flags). The two metrics you optimize on
A build's quality isn't just "did it ship." It's $ per phase (is a phase burning tokens for little signal?) and touchpoints per phase (is a phase dragging the human back in too often?). Both come from one place.
  • The cost breaker pauses at 80% of budget — an explicit human choice, never a silent overrun.
  • Touchpoints make the autonomy measurable: a phase that escalates constantly is a phase whose framework needs work.
  • Per-phase attribution turns "this build was expensive" into "P8's gap loop cost 40% — tighten the classifier."
